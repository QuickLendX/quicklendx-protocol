# Ingestion Cadence, Data Retention, and Downstream Consumers

> **Audience:** Operators & Contributors deploying, maintaining, and integrating with the QuickLendX platform.

This document describes the operational cadences (polling frequencies and schedules), the data retention policies (how long records are kept), and the downstream consumers of the QuickLendX system events and metrics.

---

## 1. Operational Cadence

QuickLendX processes events and runs system tasks on separate, dedicated schedules:

### Ledger Indexing Cadence
- **Trigger**: Ledger emission on the Stellar network.
- **Cadence**: ~5 seconds per ledger (Stellar network block time).
- **Behavior**: The indexer polls the Soroban RPC client on a continuous loop to fetch new events and update local database states.

### Lag Monitor Polling
- **Cadence**: Configured by default to 5 seconds (`5000` ms).
- **Behavior**: Periodically queries `lagMonitor.poll()` to compute the lag level (`current_ledger - last_indexed_ledger`) and update the effective degraded mode level.

### Retention Enforcement Worker
- **Cadence**: Configured via the `RETENTION_INTERVAL_MS` environment variable.
- **Default**: 24 hours (`86400000` ms).
- **Behavior**: Runs in the background, purging expired raw events, audit logs, and snapshot tables in batches defined by `RETENTION_BATCH_SIZE` (default: 500).

---

## 2. Data Retention Policies

To optimize database performance, control storage costs, and protect user privacy, different data stores have distinct retention policies.

### Backend Data Stores

| Data Store | Configuration Env Var | Default Window | Purpose / Rationale |
| :--- | :--- | :---: | :--- |
| **Raw Events** | `RETENTION_RAW_EVENTS_DAYS` | 30 days | Raw ledger transaction payloads are held briefly as they may contain sensitive KYC-adjacent data. |
| **Audit Logs** | `RETENTION_AUDIT_LOG_DAYS` | 90 days | Maintains operational traceability for administrators and automated workers (e.g. `RETENTION_RUN`). |
| **Snapshots** | `RETENTION_SNAPSHOTS_DAYS` | 14 days | Performance-critical tables holding state snapshots. Can be fully reconstructed from raw logs if needed. |
| **Webhook History** | — | 90 days | Keeps a record of webhook delivery attempts (`success` or `dead_letter` status) before cleanup. |

### Smart Contract Backup Retention

Backup retention is governed on-chain by the `BackupRetentionPolicy` and runs inside the smart contract:
- **Default Count**: Retains the 5 most recent active backups (`max_backups = 5`).
- **Default Age**: No age expiration (`max_age_seconds = 0`).
- **Auto-Cleanup**: Enabled by default (`auto_cleanup_enabled = true`), automatically evicting oldest backups when a new backup is created.
- **Archived Backups**: Protected and never pruned by automated processes.

## 3. Downstream Consumers

Events and metrics generated by the QuickLendX system are consumed by several off-chain and on-chain actors:

### Webhook Subscribers (Egress Consumers)
Downstream client systems register to receive notifications when specific contract events are published.
- **Delivery Protocol**: Webhooks are delivered via POST requests to registered subscriber URLs.
- **Payload Format**: JSON-serialised event structures matching the [Events Schema](./EVENTS_SCHEMA.md).
- **Verification**: Consumers must verify the `X-Webhook-Signature` header against the payload using their HMAC-SHA256 secret.

#### Concrete Webhook Verification Example (Node.js/TypeScript)
```typescript
import * as crypto from "crypto";

export function verifyWebhookSignature(
  payload: string,
  signature: string,
  secret: string
): boolean {
  const expectedSignature = crypto
    .createHmac("sha256", secret)
    .update(payload)
    .digest("hex");

  return crypto.timingSafeEqual(
    Buffer.from(signature, "hex"),
    Buffer.from(expectedSignature, "hex")
  );
}
```

### Ingestion Replay and CLI Tooling
Operators use the restore script to consume zipped cold archives of raw events to backfill historical state.
- **Usage**:
  ```bash
  npx ts-node scripts/restore-archived-events.ts --start 2026-04-01 --end 2026-04-30
  ```

### API Status Clients
Frontend interfaces and monitoring probes query the system status endpoint to detect if the platform has auto-degraded due to ingestion lag.
- **Endpoint**: `GET /api/v1/status`
- **Output Schema**:
  ```json
  {
    "status": "degraded",
    "lag": 12,
    "warnThreshold": 10,
    "criticalThreshold": 50
  }
  ```
